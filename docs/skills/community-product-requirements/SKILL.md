## Trigger
Use when a product objective must be converted into a bounded requirements document before implementation.

## Input
- Objective/problem statement.
- Target users and workflows.
- Known constraints and current behavior.
- Success metrics and explicit non-goals.

## Steps
1. Clarify the outcome and user problem from supplied evidence.
2. Separate requirements from assumptions.
3. Define functional and non-functional requirements.
4. Define acceptance criteria and measurable success metrics.
5. Capture dependencies, risks and open questions.
6. Keep implementation choices optional unless constrained by evidence.

## Output
- Problem.
- Goals/non-goals.
- Users/workflows.
- Requirements.
- Acceptance criteria.
- Metrics.
- Dependencies/risks.
- Open questions.

## Acceptance
- Requirements are testable.
- Metrics are measurable.
- Assumptions are labeled.
- No invented user research or market facts.
- Scope creep is excluded.

## Evidence
Link each material constraint or existing behavior to an authoritative source when available.

## Fallback
If objective or target user is ambiguous, produce only the supported sections and mark missing decisions.

## Safety
No financial commitment, Production action, credential/security mutation or destructive action.

## Non-goals
Implementation, roadmap authority, or inventing customer evidence.
